## 起動したらまず（**定期実行なので、毎回ここから**）

あなたは定期的に、毎回まっさらな状態で起動されます。前回の記憶はありません。

**期限とマーカーの確認は、あなたの仕事ではありません。**
`.github/workflows/codex-inbox.yml` が `scripts/inbox-task.mjs` を先に走らせ、
`valid_until` が過ぎているか `done_marker` が既にあるなら、
**あなたはそもそも起動されません。** あなたが動いているなら、この task は
「期限内・未実行」だと確認済みです。**もう一度確かめ直さないでください。**

**push しないでください。届きません。** あなたが動いているサンドボックスの作業場所は
チェックアウトの外にあり、リポジトリにも資格情報にも届かないように作ってあります。
2026-08-09 まで、この指示は「push できるか試して、できなければ調査せず終えろ」と
書いてありました。**この経路では push は絶対にできないので、その指示のままだと
この口は永久に空振りするだけでした。**

**あなたの回答は、ワークフローが自動でコミットします。**
完了マーカー（`done_marker`）も、あなたの回答からワークフローが作ります。
だから**あなたがやることは、下の「今回やること」を実行して、答えを書くことだけ**です。

**ファイルを探さないでください。** 2026-08-09 の最初の実行で分かったことです。
あなたは空の作業ディレクトリで起動され、`codex/INBOX.md` も git も見つけられず、
「作業ディレクトリが空です」の一文だけを返して終わりました。**それが正常な挙動です。**
だから今は、**必要なものは全部あなたへの入力に貼り付けてあります**
（この指示の全文と、`state/eta.json`・`state/constraints.json` の中身）。
毎回その場で読み出して貼っているので、**古いことはありません。**

**`## 判定` の見出しを必ず書いてください。** ワークフローはこの文字列を探して、
「本当に仕事をしたか」を判定します。無ければマーカーを置かず、明日もう一度来ます。
**中身が無いのに見出しだけ書くのはやめてください。** それは仕組みを騙すだけで、
騙した先に得をする人がいません。

**答えが空なら、マーカーも残りません。** 明日もう一度この task が来ます。
それは正しい動作です。**空振りを隠すために、中身のない答えを書かないでください。**

**「確かめられなかった」は正しい答えです。** 空振りの回に仕事を作り出さないでください。

## あなたへ

このリポジトリを読める状態で、定期的に起動されています。
**毎回まっさらな状態で始まります。** 前回何をしたかは覚えていません。それで正常です。

**推測で答えないでください。** 実際に読んだ・実行した結果だけを書いてください。
確かめていないことは「未確認」と書いてください。**未確認を「無い」と書かないこと。**

## 背景

目標は**月収20万円を最短で**。現在の売上は0円です。

この指示のあとに、次の2つの中身がそのまま貼り付けてあります。**そちらを読んでください。**

- `state/eta.json` — 到達予測と、それを縮める候補が**速い順**に
- `state/constraints.json` — 何ができて何ができないかが**測定日と再検査期限つき**で

**記憶ではなく、貼り付けられた内容で判断してください。**

## 今回やること

### 落ちた候補をもう1件調べる回ではありません

**まず、貼り付けられた `state/eta.json` の `candidates` を上から下まで読んでください。**
`refuted` が付いているものが複数あります。**その `finding` と `verdict` を読んでください。**
何件あるか・どれが落ちたかはここには書きません。書けば古くなるからです。

読むと分かりますが、落ちた理由は毎回**同じ形**をしています。
「作るものは実在する。買う人がいることも確かめられた。**速さだけが確かめられなかった**」。

前回、その形の原因を調べてもらいました。答えは
「**買い手に届く経路が値段に入っていない**」でした。それを受けて、
`candidates` に**経路そのものを中身にした候補を1件追加しました**。

### その新しい候補を、落ちた候補と同じやり方で潰しにきてください

対象は `id` が **`findable_surface_at_scale`** の候補です。中身は貼り付けた
`state/eta.json` にあります。**こちらの説明ではなく、そちらを読んでください。**

これは**こちら側が思いついた案**であり、白紙の回から出たものではありません。
つまり**身内びいきが入りやすい**。だから、落ちた候補と**同じ厳しさ**で扱ってください。
**通すために調べるのではなく、落とすために調べてください。**

調べてほしいのは次の2点です。

1. **同じ形の先例で、実際に初売上まで届いたものがあるか。**
   「個別に検索で見つかるページを多数用意し、第三者がそれを見つけて紹介し、
   そこから買い手が来た」という経路です。
   **公開日と初売上日の両方が暦日で確認できるもの**を優先してください。
   確認できないものは「日付未確認」と明記して分けてください。

2. **その形が効かなくなる条件。**
   同じ形をやって**届かなかった**先例を探してください。
   とくに、**中身が薄い大量生成ページ**がどう扱われたか
   （検索順位・掲載除外・規約・収益化可否）に実例があれば、それを書いてください。
   ここが崩れると候補ごと崩れます。**そこを狙ってください。**

**「1ページあたりに独自の計算結果が載っていれば十分か」を、実例で判断してください。**
推測での線引きは要りません。**実例が無ければ「実例なし」と書いてください。**

### 書き方

- 実例は**5件まで**。各件に、**公開日・初売上日・日数・買い手が来た経路・出典URL**
- 届かなかった実例は**3件まで**。同じ項目 ＋ **どこで止まったか**
- 最後に `## 判定` を置き、次の3つに答えてください
  - この形は、読者ゼロから初売上に届いた実例があるか（**あり／なし／日付未確認**）
  - 崩れる条件として、実例で確認できたものは何か
  - **落とすに足る材料が出たか**（出たなら、はっきり「落ちる」と書いてください）

**確かめられなかったことは「確かめられなかった」と書いてください。**
それは失敗ではありません。**埋めるために推測を書くほうが害です。**
