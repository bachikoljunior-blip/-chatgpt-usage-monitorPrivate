### 曖昧な要望を実装計画に変える

**困りごと**

作りたいものは決まっているが、着手できる粒度まで整理できていない。

**そのまま貼るもの**

```text
次の要望を、個人開発者が順番に実装できる計画へ変換してください。

要望:
<作りたいもの>

最初に、不明点のうち実装結果を大きく変えるものだけを最大3問で確認してください。確認が不要なら質問せず進めてください。

その後、次の順で出力してください。
1. 完成条件
2. 今回やらないこと
3. 実装を依存関係順に分けた作業一覧
4. 各作業の確認方法
5. 最初に着手する最小の1作業

各作業は30〜90分で完了を判断できる大きさにしてください。機能追加と無関係な全面改修は含めないでください。
```

**返ってきたら見る所**

完成条件が観察可能な言葉になっているか、最初の作業だけでも独立して確認できるかを見る。

### 原因不明の不具合を切り分ける

**困りごと**

エラーは出ているが、どこから調べればよいか分からない。

**そのまま貼るもの**

```text

症状と再現手順:
<症状・再現手順>

関連するログまたはコード:
<ログ・コード>

まだ修正案を断定しないでください。まず次を出してください。
1. 観察できる事実
2. 事実からは言えないこと
3. 原因候補を可能性順に最大5件
4. 各候補を区別する最小の確認方法
5. 最初に実行すべき確認を1つ

情報不足なら、追加で必要な情報を重要度順に最大3件だけ質問してください。秘密情報は要求せず、ログに含まれていそうなら伏せるよう指示してください。
```

**返ってきたら見る所**

原因候補と確認方法が一対一で対応し、推測が事実として扱われていないかを見る。

### 変更範囲を広げずに修正する

**困りごと**

小さな修正を頼んだのに、無関係な整理や書き換えまで入りやすい。

**そのまま貼るもの**

```text
次の修正を、必要最小限の差分で実装してください。

修正内容:
<直したいこと>

守る条件:
- 既存の公開インターフェースを変えない
- 無関係なリネーム、整形、依存関係更新をしない
- 既存の変更を上書きしない
- 修正前に対象箇所と影響範囲を確認する
- 不具合なら、可能な範囲で失敗を再現するテストを先に用意する
- 修正後に関連テストを実行する

最後に、変更したファイル、修正理由、実行した確認、未確認事項だけを簡潔に報告してください。
```

**返ってきたら見る所**

差分に依頼と無関係な変更がなく、修正を直接検証するテストがあるかを見る。

**そのまま貼るもの**

```text

<コードまたはファイル>

最初に、現在の入出力、副作用、例外、境界条件を箇条書きにしてください。既存テストが足りなければ、現在の挙動を固定する小さなテストを先に追加してください。

そのうえで、責務の分離、重複の除去、名前の改善のうち必要なものだけを行ってください。新機能、仕様変更、依存関係の追加、大規模な設計変更はしないでください。

変更後はテストを実行し、保った挙動と、判断できず触らなかった箇所を報告してください。
```

**返ってきたら見る所**

整理前の挙動が先に固定され、変更理由が「好み」ではなく具体的な問題に結び付いているかを見る。

### テストの抜けを見つける

**困りごと**

正常系のテストはあるが、どこまで信用できるか分からない。

**そのまま貼るもの**

```text
次の実装と既存テストを確認し、重要な抜けを補ってください。

対象:
<実装とテスト>

まず、入力の分類、境界値、状態遷移、失敗時の挙動、副作用を一覧にしてください。次に、既存テストが各項目を直接検証しているか対応表を作ってください。

不足分から、実害が大きく再発しやすいものを優先して最小限のテストを追加してください。実装の内部構造をそのまま写すテストや、同じ経路を値だけ変えて繰り返すテストは避けてください。

最後に、追加したテストがどの不具合を検出できるかを1件ずつ説明してください。
```

**返ってきたら見る所**

行数ではなく振る舞いを検証しているか、各テストが壊れたときに何を検出したか分かるかを見る。

### 依存関係の更新リスクを調べる

**困りごと**

ライブラリを更新したいが、壊れる場所を予測できない。

**そのまま貼るもの**

```text
次の依存関係更新について、現在のプロジェクト内だけを根拠に影響を調べてください。

更新対象:
<依存関係名と変更前後の版>

ロックファイル、設定、import、API利用箇所、型、テスト、ビルド手順を検索し、次を出してください。
1. 直接使っている箇所
2. 間接的に影響しそうな箇所
3. 破壊的変更が起きた場合に壊れやすい境界
4. 更新前に通す確認
5. 更新後に通す確認
6. 安全に戻す方法

根拠のない互換性は断定しないでください。外部情報が必要な点は「プロジェクト内の情報だけでは未確認」と明記してください。まだ更新作業は実行しないでください。
```

**返ってきたら見る所**

実際の利用箇所が列挙され、未確認の互換性が「問題なし」と処理されていないかを見る。

```text
6. 計測自体の負荷と限界を明記する

まだ最適化はしないでください。まず現状値を取得し、次に疑う箇所を計測結果から最大3件に絞ってください。
```

### セキュリティ上の事故を事前に探す

**困りごと**

公開前に、秘密情報の漏えいや危険な入力処理がないか確認したい。

**そのまま貼るもの**

```text
このプロジェクトを防御目的で確認してください。

対象:
<コードまたはディレクトリ>

次を優先して調べてください。
- 秘密情報や個人情報の混入
- 認証・認可の抜け
- 入力値の未検証
- コマンド、SQL、HTML、パスへの注入
- 危険なファイル操作
- 過剰な権限
- ログへの機密情報出力
- 本番向けでない設定

各指摘には、根拠となる箇所、成立条件、起こり得る影響、最小の修正案、確認方法を付けてください。可能性だけの指摘は「未確認」と明記してください。

秘密らしい値を見つけても内容を回答へ転載しないでください。外部への送信、認証情報の使用、実環境への攻撃は行わないでください。今回は診断だけにし、修正はまだ実施しないでください。
```

**返ってきたら見る所**

指摘に具体的な成立条件と根拠があり、単なる一般論や秘密値の再掲になっていないかを見る。

### 作業途中の状態を引き継げる形にする

**困りごと**

AIとの会話が長くなり、次のセッションで調査や失敗を繰り返してしまう。

**そのまま貼るもの**

```text
ここまでの作業を、別の担当者が会話履歴なしで再開できる引き継ぎ文書にしてください。

作業内容:
<会話履歴または作業メモ>

次の見出しをこの順で使ってください。
- 目的
- 現在の状態
- 確認済みの事実
- まだ仮説のもの
- 変更したもの
- 実行した確認と結果
- 失敗した試みと再試行しない条件
- 未解決事項
- 次に行う最小の1手
- 守るべき制約

事実と推測を混ぜず、コマンド結果やファイル名など再確認可能な根拠を残してください。秘密情報は伏せてください。完了していないことを完了扱いしないでください。
```

**返ってきたら見る所**

次の担当者が同じ調査を繰り返さずに済み、最初の一手を迷わず実行できるかを見る。
