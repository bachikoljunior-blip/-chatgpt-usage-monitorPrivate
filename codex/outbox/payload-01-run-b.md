```text
1. 直接使っている箇所
- `package.json`
  - `dependencies`: react, react-dom
  - `peerDependencies` または `devDependencies` で `@types/react`, `@types/react-dom` がある場合は合わせ更新の対象
- `src/*`
  - JSX/TSX の基本レンダリング、フック、コンポーネント木で React のレンダリングAPIを直接利用
- `package-lock.json` / `pnpm-lock.yaml` / `yarn.lock`
  - ロックされるサブ依存の範囲が広がるため、既存の依存グラフに与える波及を追跡する対象

2. 間接的に影響しそうな箇所
- テスト関連
  - React テスト環境（Jest / Vitest / Testing Library）で `StrictMode` / `act` の挙動差異が出る可能性
- ルーティング
  - `react-router-dom` 側の履歴 API、`<Link>`/`useNavigate` の型と動作差異の影響
- ビルド/型
  - Vite / webpack / Babel の設定が新ルールに対して警告を発する可能性
- 開発体験
  - `@types` 側の破壊的変更で型エラーや未使用変数警告が増える可能性
- 依存解決
  - 他ライブラリが `react@18.2.x` 固定に依存している場合、解決不能またはデュアルReact問題の温床

3. 破壊的変更が起きた場合に壊れやすい境界
- `ReactDOM.render` 系の旧API利用（`createRoot` 未移行環境）
- StrictMode で2回副作用実行される前提を置いたコード（副作用洗い出し不足）
- ルートレイアウトで `react-router-dom` のデータローダー/API前提がある場合
- Suspense / lazy boundary の既存実装（フェッチ再実行・競合更新）
- 型定義の厳密化に伴う `children` / `ReactNode` / `Dispatch` 周辺エラー
- CSS-in-JS などが `cloneElement` や `Children` API 前提で実装されている場合

4. 更新前に確認する
- ロックファイルの現状差分を確認し、更新対象だけでなく `react` 依存の受け口を列挙
  - `package.json`, `package-lock`（または `pnpm-lock`, `yarn.lock`）
- 次をまず実行
  - `npm run lint`
  - `npm test`（存在するなら）
  - `npm run build`
  - 主要経路の自動テスト（最低1本の主要画面）
- エラーパターンを事前に切り分け
  - 型エラー（TS）
  - ランタイムエラー（最小導線）
  - ルーティングエラー（履歴遷移）
- 重要: `--legacy-peer-deps` 依存状態の有無を確認しないまま更新しない

5. 更新後に確認する
- 同一チェックを更新後同順で再実行
- `react-router-dom` の主要遷移シナリオを操作して画面崩れを確認
- テスト差分が出た場合は以下で切り分け
  - 型の警告/エラーか
  - StrictMode による副作用再実行か
  - ルーティング境界のレンダリング差分か
- 本番同等環境での軽い導線確認（最低: 主要画面5経路）

6. 安全に戻す方法
- 更新直後に不具合が出た場合
  - 1) 該当更新のみを元バージョンに戻して再インストール（`npm ci`）
  - 2) 失敗範囲を1つずつ切り分けるため、`react` と `react-dom` を先に1本ずつ戻す
  - 3) 必要なら `overrides` / `resolutions` で安全な範囲に固定
- ロールバック記録テンプレ
  - 変更前 `package*.json` と lockfile のコミットを保存
  - `npm ls react` 出力を保全して依存差分比較
  - 変更理由を `CHANGELOG` 相当の記録に残す

結論
- 更新自体は「検討可能」だが、まずは「直接利用箇所」「テスト基盤」「型整合」を固定してから段階更新するのが安全。
- `react` 系の major/minor 相当更新は、動作影響だけでなくビルド/テスト資産への影響が大きいため、1回で完了させず、確認観点を持って反映すべき。
```
